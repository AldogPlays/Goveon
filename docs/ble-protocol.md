# Bluetooth investigation of the supplied Govee APK

This report concerns Govee Home 6.2.01, package `com.govee.home`, SHA-256 `833b42b39fc1c68a807adaa37fb8261ee13f52dee85c142882c6e09e7ec2d452`. REA 6.4.0 with the separately supplied JADX headless 0.7.1 provider inspected the APK without executing it. No phone, light, account credentials, or captured traffic was accessed. Decompiled methods establish the shipped implementation, not that an untested device accepts a command.

## Connection and GATT operations

`com.govee.ble.connect.BleConnectImp.connectBle` overload 1 passes the caller's auto-connect flag into `BluetoothDevice.connectGatt(context, autoConnect, callback, 2)`, selecting Android's LE transport. It stores the returned GATT object and arms a connection timeout. A pre-existing GATT prevents a second connection attempt. Evidence: `ev_ee4dffe33c9fb1d5be7be9783285c3258fe893857f7f767f04732ca0e7c5846f`.

`AbsBluetoothGattCallback.onServicesDiscovered` treats Android status zero as success and emits a `connectedSuc` event; other statuses emit `discoverServiceFail`. Service discovery is an explicit stage, rather than proof of an already operational control channel. Evidence: `ev_d4961ab334b39b1280db63c357ba1d4890a9f3a9218e9ab2f5d5f8d8ed309643`.

`BleCommImp.sendMsg` takes explicit service and characteristic UUIDs, retrieves `gatt.getService(serviceUuid).getCharacteristic(characteristicUuid)`, sets its value, and calls `gatt.writeCharacteristic`. Its boolean result means Android accepted initiation of the write; it does not itself establish the light's state. The method serializes calls and caches discovered characteristics. Evidence: `ev_f47b90d5544a275861d7f50c89d7f33ca3be17b14a3f9c1f461a911f210b0052`.

The ordinary service enablement path `BleCommImp.c` loops through characteristics, calls `setCharacteristicNotification(..., true)`, and writes descriptors with `BluetoothGattDescriptor.ENABLE_NOTIFICATION_VALUE`. The fallback characteristic lookup `e` enables notifications on the selected characteristic and writes its notification descriptor. Therefore a distinct fixed notification characteristic must not be invented from a UUID resemblance. A clean implementation should inspect notify/indicate properties, target the CCCD, and await descriptor-write callbacks; the original's sleeps are an implementation detail rather than a protocol requirement. Evidence: `ev_3600601e9a1c522ed6586087958bfa951974d0cc6a14031bf46aeebb79116253` and `ev_d7545fc8e8b54946bffa061e83c7c01a19b35f0c95ab370358636485b9b69f7f`.

## Confirmed bulb-family GATT and model mapping

The concrete `com.govee.bulblightv2.ble.BleComm` binds service `00010203-0405-0607-0809-0a0b0c0d1910` and write characteristic `00010203-0405-0607-0809-0a0b0c0d2b11`. Its static initializer assigns these constants to raw fields `x` and `y`; the respective `getServiceUuid` and `getCharacteristicUuid` getters return those fields. Evidence: `ev_1b0d783d4d44d8c898d571998229dd8d6dd1a0b6811393d055ef4a02842cb963`, `ev_0efe17b89016efa7789150863a43281cf3221d0bb3127fb8494c9d5c13bb31d6`, `ev_05aa0886bbb5a2d48aa56009a1d938e2ecacb3cf6321e602103142e89436efc1`.

Other H600-series bulbs have different types, so the model prefix does not justify granting them this color protocol. Evidence: `ev_21ec47da6fb4fceb4725a0ccd5baf0630f89d97fb1f5f5e2f009ed40bc551307`, `ev_6469378ce6b8215a2a7a69e66b1faf206c710fe13c9606d87845da5bd21f179d`, and independent asset projection `fallback_categories_dfb02909be16f14c`. Asset SHA-256: `dfb02909be16f14c221d45b90179ecaa574c22581a55fcdf9e3f209936d00e01`. This mapping is static evidence; firmware revisions and live compatibility remain untested.

The original REA bridge's Java method view omitted some static initializer blocks and produced a generic no-body placeholder. An ignored workspace copy adds a narrowly scoped call to the installed provider's `getMethodSmali` for those blocks. Resulting REA records retain the changed bridge hash, `smali` representation, and an explicit local fallback marker. The asset projection uses independent ZIP extraction and is identified separately; it is not a REA-produced record. Original installed tooling and the APK remain unchanged.

## Bulb-v3 family and adaptive model support

The supplied product asset maps H6004, H6006, H6008, H6009, H600A, H6010, and H600D to goods type 64 under Indoor Lighting / LED Bulbs. The bulb-v3 support arrays include product types 31, 64, and 111, and `SubLib.keys()` converts that exact array into registered library keys (`ev_925218be36df3c22c8cb1939e488193235978a4109f2fc025cc7958f8a8324c8`). Goveon uses the recovered type-64 set as a family profile, combined with the actual GATT channel and live status reads; it does not require a manual model exemption. Type 31's presence in the same library is insufficient to grant that dimmable product RGB or CCT controls. Evidence: independent asset projection `fallback_categories_type64_dfb02909be16f14c`, `ev_f48bc8ca98ac6fd897863a969b991591f475b28ab24c810d83ec06171d28a8c9`.

The concrete bulb-v3 `BleComm` selects the same service `00010203-0405-0607-0809-0a0b0c0d1910` and write characteristic `00010203-0405-0607-0809-0a0b0c0d2b11`; both roles are established by its own initializer and getters. Evidence: `ev_3cf06a7afdf82ba1a57a3bac8eaacd1c89c8e7f1a5ac8063643f7c224d65cea9`, `ev_311b7e302cd3d1f03c709c3e8a585d57089938a2d307720bded4bdcc5980e837`, `ev_24fe4b9ddf5690096eef9de22de1413d155e63d67cc8c9588eedaff21cf4a423`.

Bulb-v3 uses the same nine-byte color payload and selector `0x0D`, established independently by `SubModeColor.getWriteBytes` and `subModeCommandType`. Its `Support.i()` returns the white range **2700–6500 K**. The direct white factory is `SubModeColor.e(kelvin)`: it initializes primary white, clamps Kelvin to the family range, then uses the shared exact lookup through `Constant.Y`. Clamping changes endpoints only and does not round to a valid table step. Consequently this profile exposes **39 exact settings in 100 K steps** and rejects non-table inputs. Evidence: `ev_9640c8434253861d85d06b634c582bc498f0fd428b774072987131a6d67abbcd`, `ev_f55dfab8d00cc67230693b7e662f92023058c5bfb9a009614d08c2f356a7145c`, `ev_e3344faf9d41f63c88e7010ebb22df78408db954c7204631a81398209c395edf`, `ev_62e8068c0599556a1237e6c555784226747f6ce6c780976e9d9f9b894a73cd6b`, `ev_e9580864489d5737032496469dc46b6ed464acb5b2d3dbc88aad4d08742b20dc`, `ev_1bfd6ab72ee97a81b340c4b0da409a09e81aa130869b885b5e4e30ee02c26506`.

The primary white value is established through the complete helper chain: `ColorUtils.p()` calls `Companion.D()`, which calls `z(255, 255, 255)`; `z` packs alpha 255 and clamped RGB channels through `Color.argb`. The result is packed `FFFFFFFF` and serializes as RGB `FF FF FF`. Evidence: `ev_eed920fe582382904316a3c0a03e9fa0cb9a630d65f1425ada0428eed1f6c085`, `ev_311aefcad0801a6d3ad2590f79aea0bc339b72630e7c48e83f5f8539f238077c`, `ev_ec6fe41413207818c00b9f13162456257075877afd1fe31ec9ec5ea4f79f96cc`.
The separate `SubModeColor.d(color, sku)` factory passes a packed color through `KelvinHelp.b` for optional model-aware recognition of a white-palette color. It is not the direct Kelvin factory: passing a Kelvin integer to it would treat that integer as a packed color. Goveon's white action uses the explicit native-CCT payload. Evidence: `ev_a231a6a45724487515b4295b16c3de8863573d62ad98efc9e1f4ec314a8a8b75`, `ev_f85bc00472c9297461983ee40eae2da6dda476a91ad8b9f6841be6079bf92c15`.
## Shared single-command frames

The controller framework chooses `0x33` for write operations and `0xAA` for read operations. `AbsSingleController.g/f` builds the frame through `BleUtils.e`; the companion method `i` allocates 20 bytes, writes the protocol type at byte 0, command at byte 1, optional payload starting at byte 2, and XOR of bytes 0–18 at byte 19. Unused bytes remain zero. The empty read payload comes from `AbsSingleController.p` returning null. Evidence: `ev_04bc7f396a93868131410e13de40d0877c0ed5f9850e8af89c0684956b55b45e`, `ev_e413a8eed39404d6a5815af45ecc8b4186f1c3f8bc33b9ec5262b855fbf87de8`, `ev_a6e0d5e12ce3e9adc0e30ccc7539203d49d7e83e4ba7efe6dab1e313905455bd`, `ev_b5ff2a51e7f29870b2d9671c41981bde6e79f5b611630153816e078247ad2f6f`, and `ev_170fbc3c3ddfb05e6ef7e8c6c6dc86c012ce57303d1a79e54add3c4177467435`.

`SwitchController` uses command `0x01` and a one-byte payload. `BrightnessController` uses command `0x04` and a one-byte payload cast from the supplied integer. The latter constructor and serializer do not establish a universal percentage scale for every product; the UI caller and device family must corroborate the scale. Evidence: `ev_e923087a6af3001dede99875bae1249d89dd545f5504d2e7f9e3bc1be8b86311`, `ev_6c1a6173817c044d4369ff5d5e9b03f86bb7b1a7fe8e65444bf5e005958f1743`, `ev_ae6e6143bf24fd65cde9922f343a635e88265ff4801a15cdb7a9e49b3837b165`, `ev_4be221f001571c8ae15617849eeba51f3c145c21a0f4307ab50104f01b3e320e`.

`AbsSingleController.m` separates responses by the originating operation: a read extracts up to 17 bytes starting at offset 2 and calls `parseValidBytes`; a write first checks `t(response)`, then extracts 16 bytes starting at offset 3 and routes them through write-result handlers. Treating a `0x33` write response as a `0xAA` state reading would confuse acknowledgement fields with actual device state. The switch read parser interprets the first payload byte as nonzero/on. The brightness parser passes the first byte through `BleUtil.r`. Evidence: `ev_2683bd1e3024a63c16fe2165a35f5698fb38d630f889822a331dcc040c35d5ca`, `ev_58ea35a01d49ad522ceb8db9814989c9856968d9e587a8c4b514050dd7f1e858`, `ev_b95c09aaf69b31f6c4b7451d652b55aeb143ea349726aec2935ab527fc74da7b`.

## Bulb-light-v2 color mode

`com.govee.bulblightv2.ble.SubModeColor.getWriteBytes` returns nine payload bytes: `[selector, R, G, B, temperatureByte0, temperatureByte1, whiteR, whiteG, whiteB]`. Its selector is explicitly `0x0D`. `SubModeColor.b(rgb)` sets the primary packed color and clears both the temperature and white color fields. These are observations of this concrete family, not a generic color packet for all Govee products. Evidence: `ev_fc34ae5b1bc2d1d7041f835aa075d18b2a5f051d880aff9c69c2294005dfe75f`, `ev_2e2e1a471f4d1a4f77641761b8f340cd78a2e7d2d7312901641bcc965e213d9b`, `ev_100afffb28204c926c1d3e2c63debebde096b0ed50d6ab9291038c54a77044e4`.

`AbsModeController.q` directly returns the selected mode's `getWriteBytes` (`ev_9ed82e6fe6706ffa053ad6e96e06745c5b8db50452653ed5538a2d7c39252322`). The shared `AbsModeController.getCommandType` returns outer command `0x05` (`ev_195876ee3413ffbc67703c12d8e897045b5f417ffb32a85972615df931242a1a`). `BleUtil.j(value, true)` encodes the two-byte value in **big-endian** order, high byte followed by low byte (`ev_55cb479d0cf42f9b2171906beb303f3fa96a9e6129242a51c6141cf4a4b0e7a7`). This is the helper called by the bulb-v2 color serializer.

The white-temperature factory `SubModeColor.a(kelvin)` initializes primary RGB to packed `-1` (all RGB channels 255), calls `com.govee.base2home.Constant.W(kelvin)`, and sets Kelvin plus the returned white RGB only when conversion result element 0 equals 1. The conversion is an exact lookup described below, so unsupported Kelvin values must be rejected before frame creation. Evidence: `ev_65c00f2bbb4875c8d09313227d0619319ba68203f4f791d0a552d27c1873acdb`; the helper class identity is established by focused smali fallback `ev_93dcc2167fa6d3d036758b8986b6eff2fcdba9010ddf7f0f990aac646e686ec3`.

`AbsModeController.parseValidBytes` delegates to the selected mode and returns true even when no mode exists (`ev_1e05327269388cd8934c9e1ffc9acb97693eb26b69904c29049118d147e89e26`). Concrete `Mode.parseSubMode` dispatches selectors 5, 4, and 10 to microphone, scene, and DIY parsers; every other selector falls through to `SubModeColor` (`ev_29cd9bbad1d62468ae012a769f36228db78d1f7820342507c4ec0629df9d14c1`). Therefore the original parser's success is not a safe family-identification check. Goveon's independent detection must require the evidenced `0x0D` color selector and complete payload bounds. `SubModeColor.parse` expects selector-stripped data: RGB at offsets 0–2, temperature bytes at 3–4, and white RGB at 5–7 (`ev_dd424b8976c8e2b6e93d23e2ed9195c021d08c37b8c6b88e6c5485adcf4cad92`).

`AbsMode.parse` removes the first payload byte as the selector before dispatching the remaining bytes (`ev_9175e64401e30cf81872114421f8c3362cc6d2c21d18a6a3d19cc9140acb459f`). Combining this with the read-frame extraction establishes the full-packet layout for `AA 05`: selector at byte 2, RGB at bytes 3–5, temperature at 6–7, and white RGB at 8–10. The checksum remains byte 19. Unknown selectors, write acknowledgements, incomplete packets, and invalid XOR must not create reported RGB state or a supported profile.

## Bulb brightness scaling

The concrete bulb-v2 UI uses identity percentage values for its `is4H6001` path and a 20–254 device-byte scale otherwise. Its brightness widget is initialized with these respective bounds; `getRealBrightness` and `getBrightness4Show` delegate to shared conversion helpers. Evidence: `ev_7c31cbf22f37c1860b0e939025db92c47f172cd798b0201cb336c02d3667babd`, `ev_5bb0faa5e29a2ab1c5b7555153c75245475ab3cccea655c392fc4e02a3f3df7d`, `ev_ef10f97ad488e2daea8b63c840a3c58390428c52d792df45ed9428643a472e6f`.

`NumUtil.b(max, min, percent)` returns `int(min + (percent - 1) * ((max - min + 3) / 100.0f))`. Its inverse display helper is `int(ceil((raw - min) / ((max - min + 3) / 100.0f)) + 1)`. These use a Java float quotient, truncation for the outgoing byte, and ceiling for the displayed percentage. For bounds 254 and 20, 1% maps to byte 20, 50% to 136, and 100% to 254. Sending percentage 100 directly as a raw byte would limit brightness and interpreting all replies above 100 as invalid would lose real state. Evidence: `ev_b3737b3bc26210d5618c4dfb92e0e7b07891adfa241e2ad329645d6fcc8abb43`, `ev_d1a6899878403189bd50185527679cd9e1a106c9c8b96273a05bfd9a7ed4dc17`. The scale must be assigned by the traced family/model; generic runtime basic probes do not establish this byte scale.

For bulb-v3/type-64, `Support.h()` returns `[1, 100, 0]` and the concrete UI constructs `BrightnessUI(max=100, min=1, scaledDisplay=false)`. The widget sets seekbar maximum to `max - min`; on release it emits `n(progress)`, which returns `progress + min`. Consequently the maximum progress 99 emits 100. `UiV1.onBrightnessEndEvent` passes that integer directly into `new BrightnessController(value)` for BLE; the previously traced controller stores and casts that value without rescaling. Full brightness on this path therefore sends **device byte 100**, not 254. The 20–254 conversion is specific to the other recovered bulb path. Evidence: `ev_6b9316f3067878b5d52b8a6a53c5d4006cfbcb345b4b301332cacd08636e2d48`, `ev_b63ac6222c7e5f105159be11f0d6403cc88c458331d9903f83a6b63a6cc2e1d8`, `ev_fb0c0092b0d8fa79df9d912ea35e14b5de7673205895bcc02dc1d3d1f583862a`, `ev_cbfb6e9f8d7404ef7b26dbc891a2576831212e43ed69a677c7b033bdf6c704bb`, `ev_4d9db71fd752a4ea7431bcf25cf6b8ebb95aee9c5c88674b892eb798e422581b`, `ev_29f836f4a042fd60a9ef7bd2a26d6297d7ae95283321c80d8b83984b3add0ea8`, `ev_c5e79f5ba2cc12182d5ded224ffff7e8b1b85663acf71e35ce6493f72c4190a2`, `ev_4be221f001571c8ae15617849eeba51f3c145c21a0f4307ab50104f01b3e320e`.

The full brightness packet is `33 04 64 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 53`. Perceived output cannot be established from these static traces. RGB white and native Kelvin white select different payload fields, so different light output is a hypothesis to test on hardware; it does not justify changing the evidenced brightness scale.
## Verified white-temperature conversion

`com.govee.base2home.Constant.W(kelvin)` delegates to `X`. `X` rejects values outside 1800–9000 K, then searches an insertion-ordered RGB-to-Kelvin map and returns the first effective entry whose value equals the requested Kelvin. It returns `[1, kelvin, packedRgb]` on an exact match and `[0, 0, 0]` otherwise. Its advertised minimum/maximum arguments are ignored by the implementation; they do not establish a separate device range. Evidence: `ev_5442afdd2b19fbbad5a4839b6b256935ae862b883b60cc104d996422b7c76725`, `ev_c0a066243efff28bdbebb6c6420ef1e9cc09306c12d57994108cdc28f4a812fe`.

The map constructor contains 146 insertions, two color variants for each 100 K increment from 1800 through 9000. Three duplicate RGB keys are overwritten without changing their insertion position: `FFF9FD` changes from 6500 to 6600 K; `F7F5FF` from 6900 to 7000; `EFF0FF` from 7300 to 7400. The final map therefore contains 143 RGB keys and **73 selectable Kelvin values**. The selected Kelvin-to-RGB table is derived by applying these overwrites first, then taking the first match in the preserved order. This is a discrete table; interpolation or a generic Kelvin formula would change the vendor protocol values. Evidence: Java constructor `ev_74ae1150ab0d0e94ec54941b6a4e62046885ac8c861cab9ed299ec7ad060b8b0`, numeric smali verification `ev_24e2b49a81023322cfbe45b63000eca5304c9fc596c5032f7e990f2b770924cc`.

The actual bulb-v2 UI callback passes Kelvin directly to `SubModeColor.a` (`ev_f8d108b3f2a218f101c31b442314b832390281d0a4fe4b98b4d41c9497903c5b`). The shared white-feature configuration explicitly includes H6005 (`ev_d1205b36e0346fe14505595d9d25ea32f0175748f5e28234f75ddd126841b5b9`). Together with the traced product-type binding, this supports an H6005 CCT encoder. Other models on that feature list can use different protocol families. A runtime `AA 05 0D` RGB read alone does not prove white LEDs, a valid CCT range, or this lookup convention; it must not grant CCT writes to the generic `color-0d` profile.

The independently encoded CCT payload is `[0D, FF, FF, FF, KelvinHigh, KelvinLow, whiteR, whiteG, whiteB]`, carried in the existing `33 05` frame. Non-table temperatures must be rejected; the original factory's invalid-input fallback would otherwise silently become plain RGB white. Representative selected colors and full packets are:

| Kelvin | White RGB | Full 20-byte write frame |
| --- | --- | --- |
| 2000 | `FF8D0B` | `33 05 0D FF FF FF 07 D0 FF 8D 0B 00 00 00 00 00 00 00 00 6A` |
| 2700 | `FFAE54` | `33 05 0D FF FF FF 0A 8C FF AE 54 00 00 00 00 00 00 00 00 47` |
| 6500 | `FFF9FB` | `33 05 0D FF FF FF 19 64 FF F9 FB 00 00 00 00 00 00 00 00 44` |
| 9000 | `D9E1FF` | `33 05 0D FF FF FF 23 28 D9 E1 FF 00 00 00 00 00 00 00 00 08` |

The recovered range describes the shipped encoder's accepted lookup values. Physical firmware acceptance, white-channel calibration, and timing remain untested. A global UI list is initialized separately with 2000–9000 K (`ev_1c5a094f17f92ac152d1a7f88c2ba15afda85bcfbbc73f44b366b73f85222b9f`); that list does not narrow the encoder or establish every light's hardware range.

## Initialization and hardware boundary

The concrete bulb `Ble` class has no service-UUID overrides on its base connection object; its `o()` factory returns `new BleComm()` (`ev_40f7cda282fc5a03e3704371b2a2358d2fe04b6782ca4d122ca9589c8e13b6aa`). Its `F` override checks local updating/rebooting flags and otherwise delegates to `A()`. This is a connection guard, not an evidenced authorization sequence (`ev_48faa6e97b3a9a4639a356b89855f2d80367e2f66df6bc49e572c4fc16b5b840`). The separate modern `BleClientProxy` constructor accepts a nullable heartbeat message from its builder (`ev_30e72e39b7ba443caaf0bcc08b4f95291c9ea4aad5d25ce13a9be01dbe603597`). Neither observation establishes that all products require, or do not require, authentication or heartbeats.

The APK contains secret-key controllers and connect-check steps. Their existence does not justify inventing a secret or provisioning sequence for an independently discovered device. Goveon's first profile therefore sends no guessed enrollment, pairing, secret-key, reset, or heartbeat commands. Lights that require an untraced handshake may connect without accepting control; this remains a hardware-dependent limitation. No device was connected during this investigation.

For other advertised H6 lighting models, Goveon requires valid XOR-protected read replies to both `AA 01` and `AA 04` before granting basic power/brightness controls. This is runtime protocol detection by the new app, not evidence that the original APK declares every such model compatible. RGB is granted by the traced bulb-family profiles, or after receiving a valid `AA 05 0D` read with the complete recovered layout and zero reserved bytes 11–18. A different current scene/music mode cannot establish this RGB profile, so some compatible lights may initially offer only power/brightness. This conservative check can also exclude firmware variants with additional response fields. White-temperature encoding is confirmed for the recovered bulb-v2 and type-64 bulb-v3 profiles; generic Bluetooth profiles keep CCT disabled without family and range evidence. Bluetooth scenes, music modes, and segmented effects remain disabled until their family-specific encoding and capabilities are confirmed; the 1.0 release ships no scene/effect controls until their local encoding is confirmed.

| Profile | Identification | Local controls |
| --- | --- | --- |
| `bulb-v2` | H6005 from advertisement/controller label plus actual service/write characteristic | Power, percentage brightness via 20–254 device bytes, RGB, white 1800–9000 K in 100 K steps; read state |
| `bulb-v3` | Recovered type-64 bulb SKU plus actual GATT channel and live reads | Power, direct brightness 1–100, RGB, white 2700–6500 K in 100 K steps; read state |
| `common-light` | Other H6 lighting SKU plus actual GATT channel and both valid basic read replies | Power, brightness 1–100; read basic state and probe current color mode |
| `color-0d` | Common-light identification plus actual recovered `AA 05 0D` layout | Power, brightness, RGB; read basic/color state |
| `unclassified` | Recognized advertisement/service but no matching control identification | Connection only; no lighting write packets |

Generic profiles use a deliberately bounded percentage policy; the known bulb profile uses its recovered raw-byte conversion. Physical verification across firmware is still required, and the shared serializer alone does not prove universal brightness scaling. The app requests status every 20 seconds only for supported foreground connections and stops all GATT activity when backgrounded. These ordinary read requests are not a reconstruction of a vendor-specific heartbeat. There is no Android bond creation or Govee account pairing in the current direct-GATT flow.

## Coverage and unresolved checks

- Confirmed: connection transport, service-discovery result handling, notification setup mechanism, actual Android characteristic write path, shared single-command framing, switch/brightness serializers, bulb-v2 service/write UUID roles, H6005 product-type mapping, bulb-light-v2 color submode serializer, and exact discrete CCT conversion/white-channel payload.
- Pending focused trace: model-dependent authentication and heartbeat sequence, broader unsolicited notification formats, and Bluetooth scenes/effects.
- This static REA investigation performed no physical-device compatibility or timing test. Shared GATT UUIDs and an `H6` name prefix alone are insufficient evidence of a light's supported command profile. Manual Goveon testing is recorded separately in the project testing notes.

Full provider envelopes and failed-query diagnostics are retained locally and ignored by Git. Evidence IDs and relative record names are listed in the [evidence index](evidence-index.json). A 2048 MiB heap could not load the 192 MB APK (`Java heap space`), and 4096 MiB still failed class/member queries. The successful original heap allowance is restored with a single provider process at a time. Failed queries do not establish negative findings about the APK.
