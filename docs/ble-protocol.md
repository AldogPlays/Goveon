# Bluetooth investigation of the supplied Govee APK

This report concerns Govee Home 6.2.01, package `com.govee.home`, SHA-256 `833b42b39fc1c68a807adaa37fb8261ee13f52dee85c142882c6e09e7ec2d452`. REA 6.4.0 with the separately supplied JADX headless 0.7.1 provider inspected the APK without executing it. No phone, light, account credentials, or captured traffic was accessed. Decompiled methods establish the shipped implementation, not that an untested device accepts a command.

## Connection and GATT operations

`com.govee.ble.connect.BleConnectImp.connectBle` overload 1 passes the caller's auto-connect flag into `BluetoothDevice.connectGatt(context, autoConnect, callback, 2)`, selecting Android's LE transport. It stores the returned GATT object and arms a connection timeout. A pre-existing GATT prevents a second connection attempt. Evidence: `ev_ee4dffe33c9fb1d5be7be9783285c3258fe893857f7f767f04732ca0e7c5846f`.

`AbsBluetoothGattCallback.onServicesDiscovered` treats Android status zero as success and emits a `connectedSuc` event; other statuses emit `discoverServiceFail`. Service discovery is an explicit stage, rather than proof of an already operational control channel. Evidence: `ev_d4961ab334b39b1280db63c357ba1d4890a9f3a9218e9ab2f5d5f8d8ed309643`.

`BleCommImp.sendMsg` takes explicit service and characteristic UUIDs, retrieves `gatt.getService(serviceUuid).getCharacteristic(characteristicUuid)`, sets its value, and calls `gatt.writeCharacteristic`. Its boolean result means Android accepted initiation of the write; it does not itself establish the light's state. The method serializes calls and caches discovered characteristics. Evidence: `ev_f47b90d5544a275861d7f50c89d7f33ca3be17b14a3f9c1f461a911f210b0052`.

The ordinary service enablement path `BleCommImp.c` loops through characteristics, calls `setCharacteristicNotification(..., true)`, and writes descriptors with `BluetoothGattDescriptor.ENABLE_NOTIFICATION_VALUE`. The fallback characteristic lookup `e` enables notifications on the selected characteristic and writes its notification descriptor. Therefore a distinct fixed notification characteristic must not be invented from a UUID resemblance. A clean implementation should inspect notify/indicate properties, target the CCCD, and await descriptor-write callbacks; the original's sleeps are an implementation detail rather than a protocol requirement. Evidence: `ev_3600601e9a1c522ed6586087958bfa951974d0cc6a14031bf46aeebb79116253` and `ev_d7545fc8e8b54946bffa061e83c7c01a19b35f0c95ab370358636485b9b69f7f`.

## Confirmed bulb-family GATT and model mapping

The concrete `com.govee.bulblightv2.ble.BleComm` binds service `00010203-0405-0607-0809-0a0b0c0d1910` and write characteristic `00010203-0405-0607-0809-0a0b0c0d2b11`. Its static initializer assigns these constants to raw fields `x` and `y`; the respective `getServiceUuid` and `getCharacteristicUuid` getters return those fields. Evidence: `ev_1b0d783d4d44d8c898d571998229dd8d6dd1a0b6811393d055ef4a02842cb963`, `ev_0efe17b89016efa7789150863a43281cf3221d0bb3127fb8494c9d5c13bb31d6`, `ev_05aa0886bbb5a2d48aa56009a1d938e2ecacb3cf6321e602103142e89436efc1`.

`Support` initializes its product-type lists to `[20]` and registration keys to `["20"]`; `Support.a` registers this type against `GoodsType.c(1, 1)`. The supplied `assets/categories.json` maps **H6005** to goods type 20 under Indoor Lighting / LED Bulbs. It is the only product with this type in that asset. Other H600-series bulbs have different types, so the model prefix does not justify granting them this color protocol. Evidence: `ev_21ec47da6fb4fceb4725a0ccd5baf0630f89d97fb1f5f5e2f009ed40bc551307`, `ev_6469378ce6b8215a2a7a69e66b1faf206c710fe13c9606d87845da5bd21f179d`, and independent asset projection `fallback_categories_dfb02909be16f14c`. Asset SHA-256: `dfb02909be16f14c221d45b90179ecaa574c22581a55fcdf9e3f209936d00e01`. This mapping is static evidence; firmware revisions and live compatibility remain untested.

The original REA bridge's Java method view omitted some static initializer blocks and produced a generic no-body placeholder. An ignored workspace copy adds a narrowly scoped call to the installed provider's `getMethodSmali` for those blocks. Resulting REA records retain the changed bridge hash, `smali` representation, and an explicit local fallback marker. The asset projection uses independent ZIP extraction and is identified separately; it is not a REA-produced record. Original installed tooling and the APK remain unchanged.

## Shared single-command frames

The controller framework chooses `0x33` for write operations and `0xAA` for read operations. `AbsSingleController.g/f` builds the frame through `BleUtils.e`; the companion method `i` allocates 20 bytes, writes the protocol type at byte 0, command at byte 1, optional payload starting at byte 2, and XOR of bytes 0–18 at byte 19. Unused bytes remain zero. The empty read payload comes from `AbsSingleController.p` returning null. Evidence: `ev_04bc7f396a93868131410e13de40d0877c0ed5f9850e8af89c0684956b55b45e`, `ev_e413a8eed39404d6a5815af45ecc8b4186f1c3f8bc33b9ec5262b855fbf87de8`, `ev_a6e0d5e12ce3e9adc0e30ccc7539203d49d7e83e4ba7efe6dab1e313905455bd`, `ev_b5ff2a51e7f29870b2d9671c41981bde6e79f5b611630153816e078247ad2f6f`, and `ev_170fbc3c3ddfb05e6ef7e8c6c6dc86c012ce57303d1a79e54add3c4177467435`.

`SwitchController` uses command `0x01` and a one-byte payload. `BrightnessController` uses command `0x04` and a one-byte payload cast from the supplied integer. The latter constructor and serializer do not establish a universal percentage scale for every product; the UI caller and device family must corroborate the scale. Evidence: `ev_e923087a6af3001dede99875bae1249d89dd545f5504d2e7f9e3bc1be8b86311`, `ev_6c1a6173817c044d4369ff5d5e9b03f86bb7b1a7fe8e65444bf5e005958f1743`, `ev_ae6e6143bf24fd65cde9922f343a635e88265ff4801a15cdb7a9e49b3837b165`, `ev_4be221f001571c8ae15617849eeba51f3c145c21a0f4307ab50104f01b3e320e`.

`AbsSingleController.m` separates responses by the originating operation: a read extracts up to 17 bytes starting at offset 2 and calls `parseValidBytes`; a write first checks `t(response)`, then extracts 16 bytes starting at offset 3 and routes them through write-result handlers. Treating a `0x33` write response as a `0xAA` state reading would confuse acknowledgement fields with actual device state. The switch read parser interprets the first payload byte as nonzero/on. The brightness parser passes the first byte through `BleUtil.r`. Evidence: `ev_2683bd1e3024a63c16fe2165a35f5698fb38d630f889822a331dcc040c35d5ca`, `ev_58ea35a01d49ad522ceb8db9814989c9856968d9e587a8c4b514050dd7f1e858`, `ev_b95c09aaf69b31f6c4b7451d652b55aeb143ea349726aec2935ab527fc74da7b`.

## Bulb-light-v2 color mode

`com.govee.bulblightv2.ble.SubModeColor.getWriteBytes` returns nine payload bytes: `[selector, R, G, B, temperatureByte0, temperatureByte1, whiteR, whiteG, whiteB]`. Its selector is explicitly `0x0D`. `SubModeColor.b(rgb)` sets the primary packed color and clears both the temperature and white color fields. These are observations of this concrete family, not a generic color packet for all Govee products. Evidence: `ev_fc34ae5b1bc2d1d7041f835aa075d18b2a5f051d880aff9c69c2294005dfe75f`, `ev_2e2e1a471f4d1a4f77641761b8f340cd78a2e7d2d7312901641bcc965e213d9b`, `ev_100afffb28204c926c1d3e2c63debebde096b0ed50d6ab9291038c54a77044e4`.

`AbsModeController.q` directly returns the selected mode's `getWriteBytes` (`ev_9ed82e6fe6706ffa053ad6e96e06745c5b8db50452653ed5538a2d7c39252322`). The shared `AbsModeController.getCommandType` returns outer command `0x05` (`ev_195876ee3413ffbc67703c12d8e897045b5f417ffb32a85972615df931242a1a`). `BleUtil.j(value, true)` encodes the two-byte value in **big-endian** order, high byte followed by low byte (`ev_55cb479d0cf42f9b2171906beb303f3fa96a9e6129242a51c6141cf4a4b0e7a7`). This is the helper called by the bulb-v2 color serializer.

The white-temperature factory `SubModeColor.a(kelvin)` initializes primary RGB to packed `-1` (all RGB channels 255), calls `com.govee.base2home.Constant.W(kelvin)`, and sets Kelvin plus the returned white RGB only when conversion result element 0 equals 1. The conversion/range policy therefore requires its own trace; byte order alone does not prove every Kelvin value or model supports the setting. Evidence: `ev_65c00f2bbb4875c8d09313227d0619319ba68203f4f791d0a552d27c1873acdb`; the helper class identity is established by focused smali fallback `ev_93dcc2167fa6d3d036758b8986b6eff2fcdba9010ddf7f0f990aac646e686ec3`.

`AbsModeController.parseValidBytes` delegates to the selected mode and returns true even when no mode exists (`ev_1e05327269388cd8934c9e1ffc9acb97693eb26b69904c29049118d147e89e26`). Concrete `Mode.parseSubMode` dispatches selectors 5, 4, and 10 to microphone, scene, and DIY parsers; every other selector falls through to `SubModeColor` (`ev_29cd9bbad1d62468ae012a769f36228db78d1f7820342507c4ec0629df9d14c1`). Therefore the original parser's success is not a safe family-identification check. Goveon's independent detection must require the evidenced `0x0D` color selector and complete payload bounds. `SubModeColor.parse` expects selector-stripped data: RGB at offsets 0–2, temperature bytes at 3–4, and white RGB at 5–7 (`ev_dd424b8976c8e2b6e93d23e2ed9195c021d08c37b8c6b88e6c5485adcf4cad92`).
`AbsMode.parse` removes the first payload byte as the selector before dispatching the remaining bytes (`ev_9175e64401e30cf81872114421f8c3362cc6d2c21d18a6a3d19cc9140acb459f`). Combining this with the read-frame extraction establishes the full-packet layout for `AA 05`: selector at byte 2, RGB at bytes 3–5, temperature at 6–7, and white RGB at 8–10. The checksum remains byte 19. Unknown selectors, write acknowledgements, incomplete packets, and invalid XOR must not create reported RGB state or a supported profile.

## Initialization and hardware boundary

The concrete bulb `Ble` class has no service-UUID overrides on its base connection object; its `o()` factory returns `new BleComm()` (`ev_40f7cda282fc5a03e3704371b2a2358d2fe04b6782ca4d122ca9589c8e13b6aa`). Its `F` override checks local updating/rebooting flags and otherwise delegates to `A()`. This is a connection guard, not an evidenced authorization sequence (`ev_48faa6e97b3a9a4639a356b89855f2d80367e2f66df6bc49e572c4fc16b5b840`). The separate modern `BleClientProxy` constructor accepts a nullable heartbeat message from its builder (`ev_30e72e39b7ba443caaf0bcc08b4f95291c9ea4aad5d25ce13a9be01dbe603597`). Neither observation establishes that all products require, or do not require, authentication or heartbeats.

The APK contains secret-key controllers and connect-check steps. Their existence does not justify inventing a secret or provisioning sequence for an independently discovered device. Goveon's first profile therefore sends no guessed enrollment, pairing, secret-key, reset, or heartbeat commands. Lights that require an untraced handshake may connect without accepting control; this remains a hardware-dependent limitation. No device was connected during this investigation.

For other advertised H6 lighting models, Goveon requires valid XOR-protected read replies to both `AA 01` and `AA 04` before granting basic power/brightness controls. This is runtime protocol detection by the new app, not evidence that the original APK declares every such model compatible. RGB is granted by the traced H6005 profile, or after receiving a valid `AA 05 0D` read with the complete recovered layout and zero reserved bytes 11–18. A different current scene/music mode cannot establish this RGB profile, so some compatible lights may initially offer only power/brightness. This conservative check can also exclude firmware variants with additional response fields. Temperature, Bluetooth scenes, music modes, and segmented effects remain disabled until their family-specific encoding and capabilities are confirmed; developer-API capabilities can expose supported equivalents independently.

| Profile | Identification | Local controls |
| --- | --- | --- |
| `bulb-v2` | H6005 from advertisement/controller label plus actual service/write characteristic | Power, brightness 1–100, RGB; read power/brightness/color |
| `common-light` | Other H6 lighting SKU plus actual GATT channel and both valid basic read replies | Power, brightness 1–100; read basic state and probe current color mode |
| `color-0d` | Common-light identification plus actual recovered `AA 05 0D` layout | Power, brightness, RGB; read basic/color state |
| `unclassified` | Recognized advertisement/service but no matching control identification | Connection only; no lighting write packets |

The percentage range is a deliberately bounded implementation policy and still requires physical verification across firmware; shared serialization alone does not prove universal brightness scaling. The app requests status every 20 seconds only for supported foreground connections and stops all GATT activity when backgrounded. These ordinary read requests are not a reconstruction of a vendor-specific heartbeat. There is no Android bond creation or Govee account pairing in the current direct-GATT flow.

## Coverage and unresolved checks

- Confirmed: connection transport, service-discovery result handling, notification setup mechanism, actual Android characteristic write path, shared single-command framing, switch/brightness serializers, bulb-v2 service/write UUID roles, H6005 product-type mapping, and bulb-light-v2 color submode serializer.
- Pending focused trace: Kelvin conversion, model-dependent authentication and heartbeat sequence, and broader unsolicited notification formats and Bluetooth scenes/effects.
- No physical-device compatibility or timing test has been performed. Shared GATT UUIDs and an `H6` name prefix alone are insufficient evidence of a light's supported command profile.

Full provider envelopes and failed-query diagnostics are retained locally and ignored by Git. Evidence IDs and relative record names are listed in the [evidence index](evidence-index.json).
